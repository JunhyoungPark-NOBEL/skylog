# 이메일 로그인 연결 보완 — 2026-09-09

메일 링크가 APK 또는 iPhone 홈 화면 웹앱과 다른 브라우저로 열릴 때 로그인 요청 정보가 이어지지 않는 문제를 보완했다. 이번 변경은 이메일 확인을 유지하며, 인증번호가 없는 메일에 번호 입력을 요구하지 않는다.

## 확인한 원인과 서버 상태

- 기존 클라이언트는 Supabase PKCE를 사용했다. 요청한 앱의 저장소에 생성한 verifier가 메일 앱의 외부 브라우저에 없으면 코드를 세션으로 교환할 수 없다. [Supabase PKCE 문서](https://supabase.com/docs/guides/auth/sessions/pkce-flow), 설치 SDK `@supabase/auth-js 2.116.0`의 실제 교환/저장소 구현을 확인했다.
- 기존 시작 처리는 query `code`만 읽었으며, hash/query 오류·네이티브 앱 URL 복귀를 처리하지 않았다. 메일 전송 이후에는 새로고침으로 입력 단계가 사라지고, 같은 주소로 재전송하는 동작도 없었다.
- 루트 작업의 서버 읽기 점검에서 이메일 로그인이 활성화되어 있고 이메일 확인은 켜져 있다. 기본 무료 SMTP이며 메일 양식 수정은 현재 사용할 수 없고, 실제 메일 제목은 `Your sign-in link`다. 초기에는 추가 redirect가 없었다(`artifacts/qa-build15/auth-server-readonly.json`). 이후 루트가 정확한 네이티브 주소 `io.github.junhyoungparknobel.skylog://login` 한 개를 허용 목록에 저장하고 다시 읽어 확인했다. 사이트 URL은 기존 HTTPS 웹앱 주소를 유지한다.
- `VITE_COMMUNITY_EMAIL_CODE=false`, `VITE_COMMUNITY_SIGNUPS_READY=false`를 유지한다. 인증번호 방식은 서버의 메일 본문에 `{{ .Token }}`가 포함되어야 한다. [Supabase 이메일 로그인 문서](https://supabase.com/docs/guides/auth/auth-email-passwordless). 무료 기본 SMTP를 일반 사용자 대상 SMTP 개통으로 표시하지 않는다.
- 서버 변경은 위 네이티브 redirect 한 개 추가뿐이다. SMTP/이메일 확인/가입 플래그는 바꾸지 않았으며 이메일 발송, 실제 새 계정/댓글 생성은 하지 않았다.

## 사용 방법

### Android 설치 앱

1. 업데이트한 APK의 계정 화면에 이메일을 입력하고 로그인 메일을 받는다.
2. 메일의 로그인 버튼을 누른다.
3. 메일 링크가 설치 앱으로 돌아오면 원래 앱의 verifier로 확인을 마친다. 브라우저가 앱 열기 확인을 표시할 수 있다. 이전에 받은 HTTPS 링크에서 복구 화면이 나타나면 **설치한 앱에서 계속**을 누른다.

앱이 종료된 경우와 이미 실행 중인 경우 모두 Capacitor `getLaunchUrl`/`appUrlOpen`으로 받는다. Android manifest와 iOS URL scheme을 추가했고, 기존 iOS SceneDelegate의 Capacitor URL 전달을 확인했다. [Capacitor App 문서](https://capacitorjs.com/docs/apis/app).

설치 앱에서만 `emailRedirectTo`를 등록된 네이티브 주소로 지정한다. [Supabase 모바일 이메일 딥링크](https://supabase.com/docs/guides/auth/native-mobile-deep-linking)와 [redirect 설정](https://supabase.com/docs/guides/auth/redirect-urls)이 지원하는 흐름이다. 구 APK는 redirect를 지정하지 않으므로 바뀌지 않은 HTTPS Site URL을 사용한다. 웹/iPhone 홈 화면 앱도 HTTPS를 유지한다. 메일 앱이 외부 앱 열기를 막으면 원본 링크 붙여넣기 복구를 사용할 수 있다.

### iPhone 홈 화면 앱 또는 다른 브라우저

1. 원래 앱에서 메일을 요청한다.
2. 메일 버튼이 다른 브라우저의 복구 화면으로 열리면 **복구 링크 복사**를 누른다.
3. 원래 홈 화면 앱으로 돌아가 **로그인이 안 되나요?**를 열고 링크를 붙여넣은 뒤 확인한다.

같은 브라우저에서 요청하고 연 경우에는 바로 로그인한다. 복구 링크는 5분 안에 사용한다. 복사나 확인이 계속 실패하면 원래 앱에서 새 메일을 받고, 메일의 로그인 버튼을 길게 눌러 원본 링크를 복사해 같은 입력란에서 확인할 수 있다. 이미 사용한 링크는 새로 받아야 한다.

### 메일 확인 화면

- 메일 주소와 성공한 요청 시각만 최대 1시간 복원한다. 번호·링크·세션 토큰은 요청 단계 저장소에 넣지 않는다. 저장소 접근이 막힌 경우 같은 실행에서는 메모리로 유지한다.
- 메일 확인 단계에서 60초 후 다시 받기, 다른 이메일 사용, 접힌 복구 도움말을 제공한다. 이 60초는 기본 서버 제한에 맞춘 UI 대기이며 실제 서버 제한은 서버 응답이 최종 판단한다.
- 전송/확인 중 입력과 다른 요청을 잠그고 중복 전송을 막는다. 화면을 벗어난 뒤 늦은 응답이 새 요청 상태를 덮어쓰지 않는다.
- OTP 구성은 코드상 유지하되, 실제 번호 메일 양식이 확인되기 전에는 켜지 않는다.

## 인증 및 실패 경계

- 콜백의 code, flow ID, 오류, 이전 implicit 토큰을 파싱하고 URL에서 즉시 제거한다. 서버의 원문 오류 설명이나 자격 증명을 UI/로그에 노출하지 않는다. 이전 implicit 링크는 새 메일로 복구하며 해당 토큰을 설치하지 않는다.
- 네이티브 복귀와 웹앱 복구는 PKCE verifier 검증을 유지한다. 복구 주소는 현재 배포 웹앱 또는 등록된 네이티브 로그인 주소만 허용하며, 다른 origin/경로·userinfo·중복 파라미터를 거부한다. 임의 URL을 열거나 fetch하지 않는다.
- 원본 메일 링크는 현재 Supabase 프로젝트의 `/auth/v1/verify`와 이메일 확인 type만 받는다. 세션을 저장하지 않는 격리 클라이언트에서 먼저 검증하고, 이 앱에서 실제 요청한 이메일과 반환 이메일이 일치하며 그 요청이 아직 최신인 경우에만 주 클라이언트에 세션을 적용한다. 격리 확인 중 다른 로그인이 완료되어 현재 user가 바뀌었으면 늦은 결과를 적용하지 않는다. 미일치/만료도 기존 세션을 바꾸지 않는다.
- 붙여넣은 링크는 요청 시작 즉시 입력란에서 지운다. 복구 링크는 브라우저 메모리에만 한시적으로 두며 사용자 클릭으로만 클립보드 또는 앱에 전달한다.
- 네이티브 시작과 URL 이벤트의 동일 코드는 한 번만 소비한다. 이미 다른 코드가 교환 중인 경우 새 이벤트로 병렬 교환을 시작하지 않으며, 뒤늦은 오류 URL도 확인 중 상태를 풀지 않는다. 실패한 코드 재시도를 5분 동안 차단하지 않는다. 설치 앱 자체에서 verifier가 없으면 자기 자신으로 돌아가는 버튼이나 다른 앱에 붙여넣기 안내를 표시하지 않고 새 메일 요청 화면을 열어 준다.
- 설치 SDK는 일부 네트워크 실패에서도 verifier를 제거하므로 같은 코드 재시도를 보장하지 않는다. 연결 복구 후에도 실패하면 새 메일을 요청하도록 안내한다. 코드 교환의 느린 서버 응답이 앱 전체 시작을 막지 않도록 계정 화면에 확인 중 상태를 표시한다.
- 외부 브라우저가 이미 다른 계정으로 로그인되어 있어도 새 링크의 확인·오류·복구 안내를 우선 표시한다. 현재 계정 이메일과 새 링크 결과를 구분하며, 확인 중에는 계정 작업을 감춘다. 실패 뒤 **현재 계정으로 돌아가기**는 안내만 닫고 기존 세션·로컬 자료를 보존한다.

## 검증

- 새 로그인 단위 검사 **32개 통과**. 실제 Supabase SDK로 verifier 없는 브라우저의 교환 거부, 원래 앱의 성공/중복 이벤트, 격리 검증·타인 링크·만료·요청/세션 변경·저장소 차단, native redirect 분기와 UI 비동기, 기존 계정이 있는 콜백 안내를 확인한다. 전체 검사 수치와 최종 소스는 [모바일 검증 보고](MOBILE-RELEASE.md)를 따른다.
- Chromium 로그인 시나리오 **8개**: `tests/e2e/auth.spec.ts`. 같은 브라우저 로그인, 별도 브라우저에서 실패 후 원래 앱에 복구, Android 복귀 링크, 오류 URL 정리, 요청 단계 복원/잘못된 링크, 360px 영어125%, 로그인된 외부 브라우저의 세션·북마크 보존, 느린 콜백·만료 구분을 포함한다. 모든 Supabase 호출을 라우트로 가로채며 실제 메일을 보내지 않는다. 최종 전체 실행 결과는 [모바일 검증 보고](MOBILE-RELEASE.md)에 기록한다.
- Android 계측 소스 **2개 컴파일 완료**. 실제 계측 실행 결과는 루트 실행 대기이며, 컴파일을 기기 실행 통과로 표시하지 않는다.
- 단위 검사와 네이티브 이벤트 모킹은 실제 휴대폰의 메일 앱 복귀 성공을 뜻하지 않는다. 새 APK 설치 후 Android 메일 앱→브라우저→설치 앱, 실제 iPhone 홈 화면 앱→메일→Safari→홈 화면 앱 복구는 사용자 확인이 필요하다. Apple 서명/TestFlight와 일반 가입 SMTP 개통도 별도다.
